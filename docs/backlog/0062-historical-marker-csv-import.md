## User story

As a user who has five years of past labs in a portal — or in a spreadsheet I keep myself — and only the most recent PDF on hand, I want to paste a small CSV ("date, marker, value, unit") on the Labs page and have Almanac materialize one panel per distinct draw date, with each row canonicalized through the existing marker resolver and flagged against the functional range, so that my trend rules in the insight engine and the sparklines on Progress have years of data to read from immediately, instead of being limited to "the panels I happen to have a PDF for."

## Why now (four lenses)

### Product Owner

The product's three deepest moat assets — the **persistent timeline**, **marker canonicalization**, and the **insight engine's trend rules** — all reward density: the longer the dated value series for any one marker, the more meaningful the sparkline, the more reliable the trend rule's "persistently elevated across N draws" verdict, and the smarter the next plan-compose's "since-last-draw" framing. Today the only on-ramp to that density is uploading a PDF/image (which extracts via Claude Vision) or typing values into the manual panel form one draw at a time. Neither suits the user who already has years of historical numbers in a portal export or a personal spreadsheet — pasting a single CSV is the natural shape of that data, and pasting it should produce panels exactly as if they had each been uploaded. The smallest meaningful unit of value is a "Paste historical values" affordance on the Labs page (beside the existing PDF-drop and manual-panel paths) that accepts a CSV (header row required: `date, marker, value, unit`; optional `lab` column), parses it in pure TypeScript with no LLM call, canonicalizes each marker via the existing `findMarker()` resolver, classifies each value via `flagFor()` against the resolved marker's ranges, groups rows by `date` into one `Panel` per draw, and persists the panels through the same `addPanel(...)` path the extraction and manual flows already use. Before write, a confirmation step shows the parsed panels, the canonicalization outcomes (recognized rows vs unrecognized — which route through the existing match-unrecognized flow), and the per-row flag, so the user reviews exactly what is about to land in their timeline. No new Anthropic call, no new schema, no new persistence path.

### Stakeholder

This is the cheapest possible move to deepen the **persistent timeline**, the **canonicalization** moat, and the **insight engine's trend rules** in one stroke — the trend rules in `insights.ts` (`TREND_RULES`) become useful only with multi-draw history; today most users have at most one or two draws of any marker, so the rules rarely fire. A CSV import unlocks the engine's full reasoning capacity on day one for any user with historical data — exactly the engaged early-adopter who knows their numbers and is looking for the product to do something with them that a chat box cannot. A wrapper has no canonical marker store to resolve `25-OH Vit D` and `Vitamin D, 25-OH` to the same key, no per-marker functional range to classify against, no dated panel store to group into, and no trend-rule engine to read the result; "paste five years of ferritin values and watch the trend rule fire" is structurally a feature of a product with all four. It compounds the shipped paste-as-text flow (0046) — that path is single-panel and unstructured; this is multi-panel and structured. And it is privacy-clean by construction: the parse is a pure TypeScript transform with NO Anthropic call (the extractor's vision pipeline is not involved), so a user can backfill a decade of biology with zero egress beyond the standard plan-compose that runs later.

### User (at 7am on the phone)

I have my ferritin, ApoB, fasting insulin, and vitamin D across eleven dates from the last five years, in a spreadsheet I keep in iCloud. On the Labs page, a quiet affordance: "Paste historical values." I tap it; a textarea opens with a one-line schema example: `date, marker, value, unit` and an "lab (optional)" hint. I paste my forty rows. A preview panel materializes below: eleven dated panels appear, oldest at the bottom, with the marker names I typed canonicalized to their library names (the `25-OH Vit D` row resolves to "Vitamin D, 25-hydroxy" with a small "recognized" mark; one row I typed as `OmegaIndex` shows "unrecognized" with a "match this" link to the existing flow). Each row carries its flag — optimal / suboptimal / low / high — against the same functional range the rest of the app reads. I tap "Save 11 panels." They land in the timeline. I navigate to Progress and my ferritin sparkline now spans five years, with the functional band behind it, and the engine's trend rule fires for "ferritin persistently below 50 across the last three draws." It worked offline, instantly, because the parse and the canonicalization are local — no Claude call, no upload, no spinner.

### Growth

This is a moat-deepening ticket with a strong retention tail and a real acquisition pull. (Hypothesis: a CSV import that materializes years of history in one paste is the single highest-leverage day-one feature for the literate prospect with years of past labs — exactly the precision-health-fluent persona the product targets — because it converts the cold-start "I have one PDF" problem into "the engine has my decade," which is the difference between a sparkline and a trend, and the difference between a generic plan and one whose insights name "ferritin has sat below 50 across your last four draws"; back-of-envelope from how data-rich onboarding paths outperform single-data-point ones for technical users in self-tracking; treat as untested without remote analytics, which we will never add.) The "show me" frame is the multi-year sparkline that materializes seconds after a paste: a screenshot of "my ferritin trend across 2021–2026, with the functional band, from a single paste" is the artifact the persona forwards to the friend with the same shoebox of past labs — the friend who would never re-upload five PDFs but will paste a single CSV. It is the structured, multi-panel sibling of the paste-as-text flow (0046, shipped): that handles "the values from the patient portal page I'm looking at right now"; this handles "the spreadsheet I've kept for five years."

## Acceptance criteria

Each box maps 1:1 to a Playwright test scenario.

- [ ] `src/labs/csv-import.ts` (new) exports `parseHistoricalCsv(text: string): { rows: ParsedRow[]; errors: ParseError[] }`. It parses a CSV with a required header `date,marker,value,unit` (case-insensitive; trimmed) and an optional `lab` column; tolerates Windows and Unix newlines, quoted fields, and a leading BOM. Each row yields `{ date: Day, marker: string, value: number, unit: string, lab?: string }` or a structured error keyed by row index. The parser is pure: no DOM, no Dexie, no network, NO Anthropic call. Asserted with a multi-row fixture exercising quotes, BOM, mixed line endings, the optional column, and a row missing a required field.
- [ ] `src/labs/csv-import.ts` also exports `buildHistoricalPanels(rows: ParsedRow[], allMarkers: MarkerDef[]): { panels: Panel[]; unrecognized: { rowIndex: number; raw: string }[] }`. It canonicalizes each row's `marker` via `findMarker()` against the merged seed + user-defined marker set, groups rows by `date` into one `Panel` per distinct date (each panel carries a synthesized `id`, the `drawnAt = date`, the optional `lab` if present on any row of that date else empty, and the parsed `results[]` with canonical `markerKey`, `value`, `unit`, range fields filled from the resolved marker, and `flag` computed via `flagFor()`), and reports rows whose marker did NOT resolve as `unrecognized`. Pure: no Dexie, no network. Asserted by passing a known row set and confirming the grouped panels, canonical markers, computed flags, and unrecognized list.
- [ ] The Labs page (`src/pages/labs.ts`) renders a "Paste historical values" affordance beside the existing PDF-drop and manual-panel actions. Tapping it opens a textarea with the schema example as placeholder copy ("date, marker, value, unit — e.g. `2024-03-04, Ferritin, 32, ng/mL`. Optional `lab` column."). The textarea accepts paste of any reasonable size for a CSV (no artificial char cap; the spec asserts a 200-row paste parses). Asserted by tapping the action and confirming the textarea + example render.
- [ ] After paste, a "Preview" step renders BEFORE any write to IndexedDB: the parsed panels in the order they will be saved (newest-first, matching the labs list ordering), each row showing canonical marker name + value + unit + flag chip, with unrecognized rows tagged "unrecognized" and offered a single tap into the existing match-unrecognized flow. Parse errors render as a small list with row numbers and a one-line reason ("row 7: missing value"). NO panel is persisted until the user taps "Save N panels." Asserted by pasting a mixed CSV and confirming the preview content matches `buildHistoricalPanels(...)` and that no `panels` row is written until the save tap.
- [ ] Tapping "Save N panels" persists each panel via the SAME `addPanel(...)` path the manual and extraction flows use (no new persistence helper, no schema migration). After save, the user lands on the labs index showing the newly-added panels, oldest-first by `drawnAt`, mixed with any pre-existing panels in the standard sort. Asserted by saving and confirming the labs index shows the new panels and the existing panels in the documented order.
- [ ] Tapping "Cancel" on the preview step discards the parsed panels with NO write to IndexedDB; reopening the affordance gives a fresh textarea. Asserted by previewing, canceling, and confirming the `panels` table count is unchanged.
- [ ] Unrecognized markers route through the EXISTING match-unrecognized flow (the affordance Labs already has for extractor outputs that did not resolve). After a match is recorded, re-running the preview (or proceeding to save) canonicalizes the previously-unrecognized rows to the matched marker on the freshly-built panels. Asserted by pasting an unrecognized marker, matching it, re-previewing, and confirming the row now carries the canonical key.
- [ ] Duplicate dates ARE allowed (multiple rows of different markers on the same date roll into ONE panel — this is the entire point). A second paste containing a row on an EXISTING date does NOT auto-merge into the prior panel — it creates a separate panel that the user can review (the auto-split rule from 0001 still applies: distinct `drawnAt` → distinct panel; identical `drawnAt` → user's existing dedupe affordance). Document the chosen behavior and assert it: a CSV with two rows on 2024-03-04 creates ONE panel with two results; pasting again with another row on 2024-03-04 creates a second panel with one result (not auto-merged), consistent with the manual-panel behavior on the same date.
- [ ] The parse and the canonicalization make **zero Anthropic calls** and **zero network calls** — they are pure local transforms. Asserted by pasting, previewing, saving 11 panels, and confirming the mock recorded zero requests across the whole flow.
- [ ] The Anthropic key NEVER appears in the textarea echo, the preview, the persisted panels, or any intermediate string. Asserted by seeding a sentinel key and confirming it appears nowhere in the rendered preview or the saved panel rows.
- [ ] After save, the existing Progress page sparklines (`src/pages/progress.ts`) and the existing insight-engine trend rules (`src/insights.ts` `TREND_RULES`) read the new panels exactly as if they had been uploaded — no new code path required. Asserted by pasting a multi-date series for a marker the trend rules know (e.g. ferritin), composing a plan, intercepting the plan-compose prompt, and confirming the deterministic findings block contains the trend rule's verdict (the rule fired). For users with no LLM-call appetite in this spec, separately assert the sparkline on Progress carries the new dated points (`viz.ts` sparkline path data length matches the seeded count).
- [ ] User-defined markers (0002) and sex-specific keys: a CSV row whose marker name matches a user-defined marker resolves to that key; a sex-specific marker (e.g. `Ferritin` on a male profile) resolves to `ferritin_m` via `findMarker(...)`. Asserted by pasting one of each and confirming the canonical key on the persisted result.
- [ ] Unit handling: a row whose unit matches the resolved marker's canonical unit is accepted verbatim; a row whose unit is the marker's documented alternate unit (e.g. nmol/L for vit D when the canonical is ng/mL) is flagged in the preview ("unit differs — converted to <canonical> via 0044") IF 0044 has shipped; otherwise the row is flagged "unit differs — value persisted as typed, flag computed against <canonical> may be misleading" and the row is highlighted but still importable. Document the chosen behavior per the 0044 status at implementation time. Asserted with one row in canonical units and one in an alternate unit.
- [ ] Parse errors are gracefully surfaced: a missing header row, a malformed date, a non-numeric value, or a missing required field renders an inline error list with row indices and reasons; the "Save N panels" button is disabled when ANY row in the parsed set is in error (the user fixes the CSV and re-pastes). Asserted with three malformed inputs and confirming each renders the right inline reason and disables save.
- [ ] Renders on both **chromium and mobile-webkit**. The affordance and the textarea fit the 390 px viewport; the preview panel list wraps cleanly; the save and cancel actions are ≥44×44 css px (`box-sizing: border-box; min-height: 45px`). The textarea remains usable with paste from the mobile-webkit clipboard. Asserted on both projects.
- [ ] Tour mode (0014) and shared-view mode (0017) do NOT offer the affordance (neither mode has a real timeline to write to; `addPanel` already short-circuits both). Asserted in both modes.
- [ ] The existing Labs flows — the PDF/image drop, the paste-as-text flow (0046), the manual-panel form, the match-unrecognized flow, the panel detail with the report card (0036) / canonicalization receipt (0026) / movement receipt (0032), the labs list ordering — are byte-for-byte unchanged in behavior; the CSV import is purely additive. Asserted by exercising each existing flow and confirming it is unchanged.
- [ ] Privacy E2E (`tests/e2e/privacy.spec.ts`) still passes — the import is a local read/parse/write with no inference; no new hostnames.
- [ ] Schema migration: **no** — the import writes through the existing `addPanel(...)` path and the existing `panels` / `results` shape. Nothing new is persisted.
- [ ] New `tests/e2e/csv-import.spec.ts` covers: parse over a multi-row fixture (quotes, BOM, mixed line endings, optional `lab`, malformed rows); `buildHistoricalPanels` grouping + canonicalization + flag computation; the affordance opens, the textarea accepts paste, the preview renders before any DB write; save persists via `addPanel`, cancel does not; unrecognized markers route to the existing match flow; duplicate-date handling per the documented rule; zero Anthropic + zero network across the full flow; the key never appears (sentinel); the trend-rule firing test on a seeded multi-date ferritin series; user-defined + sex-specific marker resolution; unit handling per the 0044-shipped state; parse-error rendering and save-disabled when in error; tour vs shared-view absence; the existing Labs flows unchanged; mobile rendering.

## Out of scope

Explicit anti-goals. The dev agent will not do these even if they seem related.

- An LLM call to parse, normalize, or canonicalize the CSV. The parse is pure TypeScript; the marker resolver is the existing `findMarker()`; the flag is `flagFor()`. A Claude call would add cost, latency, non-determinism, and an egress to a feature whose entire value is being instant, local, deterministic, and provably honest about what it imported.
- A drag-and-drop file path (drop an `.csv` file). v1 is paste-into-textarea, mirroring the 0046 paste-as-text affordance — file-drop is a possible follow-up (and adds zero value over paste for a multi-thousand-row max use case).
- Importing units the marker DB does not know. v1 supports the canonical unit and (if 0044 has shipped) the canonical's documented alternate unit; novel units are flagged "unit differs" but persisted as typed with a clear caveat. A full unit-conversion pipeline beyond 0044's table is out of scope.
- Importing labs (the lab name) beyond an optional column the panel stores. No lab-side normalization, no per-lab quirks pipeline.
- Auto-merging a pasted row whose `drawnAt` matches an existing panel. v1 follows the 0001 auto-split rule: distinct date → distinct panel, identical date → separate panel (user can dedupe via the existing affordance). A "merge into existing panel" path is a possible follow-up.
- A per-cell editor on the preview. v1 lets the user cancel, fix the CSV, and re-paste — that is the simplest correct flow. An inline cell edit is a possible follow-up.
- Carrying the CSV import into the doctor PDF (0010/0016), the share link (0017), the Markdown export (0027), or the coach packet (0048) as a separate section. The imported panels participate in those exports exactly as any other panel does — there is no "imported" tag.
- A "download a sample CSV" link or any external resource. The textarea's placeholder copy carries the schema example; we have no backend to host a sample, and the inline example is sufficient.
- Reverse direction (CSV EXPORT of the timeline). The Markdown export (0027) already gives the readable longitudinal record; a CSV export is a possible separate ticket.

## Engineering notes

Files / patterns the dev should touch. Be specific enough that the dev doesn't have to re-discover the architecture.

- `src/labs/csv-import.ts` (new) — `parseHistoricalCsv(text)` and `buildHistoricalPanels(rows, allMarkers)`.
