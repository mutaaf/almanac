## User story

As a user whose new lab reports total cholesterol in mmol/L when every prior draw was in mg/dL — or fasting glucose in mmol/L against a prior mg/dL, or vitamin D in nmol/L against a prior ng/mL — I want the moment that panel resolves to tell me, plainly, that the app recognized the different unit and converted it onto my existing trend ("LabCorp reported total cholesterol in mmol/L; converted to 193 mg/dL to join your line — now 3 draws on one scale"), so that switching to a lab that reports in a different unit does not silently fork my trend into two unrelated half-lines or quietly drop the new reading, and so the sparkline on Progress is one honest series on one scale instead of two numbers that only look comparable.

## Why now (four lenses)

### Product Owner

Marker canonicalization (0026) reconciles markers across labs that *name* them differently. It explicitly does NOT reconcile labs that *measure* them in different units — 0026's out-of-scope names this as "a distinct mechanism ... worth its own honest surface." That surface is missing, and the gap is real: the `MarkerDef` already carries `altUnits: { unit; toCanonical }[]`, so the conversion data exists, but nothing converts a draw whose `Result.unit` differs from the canonical `MarkerDef.unit` (or from a prior draw's unit) onto the trend, and nothing tells the user it happened. Today a user who switches from a mg/dL lab to a mmol/L lab gets, at best, a trend that plots 5.0 (mmol/L cholesterol) next to 193 (mg/dL) as if they were the same scale — which is biologically meaningless — or, at worst, a dropped reading. The smallest meaningful unit of value is two coupled, deterministic, zero-network pieces: (1) at extraction/result-store time, when a result's unit is a known `altUnit` of its resolved marker, convert the value to the canonical unit and store the canonical value (preserving the originally-reported value + unit alongside it), and (2) a "unit reconciled" receipt line on the post-extraction review screen naming the conversion. It reuses the conversion factors already in the marker DB; the only new code is applying them at store time and the receipt sentence. It makes the trend correct, and it makes the correction legible.

### Stakeholder

This deepens the **marker canonicalization** moat along its second, harder axis — units, not just names — and it directly protects the **persistent timeline**, whose entire value is that a trend survives switching labs. Name canonicalization (0026) lets the timeline span report *formats*; unit canonicalization lets it span report *scales* — and a user who moves to a lab in a different unit system (common when changing clinics, insurers, or countries) is exactly the user whose timeline is most at risk and most valuable to retain. It is a sentence the chat box structurally cannot produce honestly: raw Claude pasted two screenshots will not recognize that 5.0 mmol/L and 193 mg/dL are the same cholesterol on different scales and silently reconcile them onto one trend with the factor stated — it has no canonical unit, no per-marker conversion table, and no prior series to align to. Almanac has all three. It is the unit sibling of the movement receipt (0032) and the name receipt (0026): 0026 says "we recognized this marker across labs," 0044 says "and we put it on one scale," 0032 says "and here is how far it moved." Together they make the timeline trustworthy enough to build a year of decisions on, on-device, with the conversion factor shown so the user can check our arithmetic.

### User (at 7am on the phone)

New labs, new clinic — and this one reports in metric. The review screen resolves and, under total cholesterol, a quiet line: "LabCorp reported this in mmol/L; converted to 193 mg/dL using ×38.67 to join your line — now 3 draws on one scale." Under vitamin D: "Reported in nmol/L; converted to 48 ng/mL." It is the annoying spreadsheet arithmetic I would otherwise do by hand to keep my trend honest, done for me, with the factor shown so I can check it. I tap through to Progress and the sparkline is one continuous line on one scale — not the broken double-line I half-expected. A marker whose unit the app does not have a conversion for says so honestly rather than guessing — it stays out of the converted trend and tells me why. It rendered instantly, offline, because the conversion factors ship in the app and the math is local.

### Growth

This is a moat-and-retention ticket whose specific audience is the user most likely to have an otherwise-broken trend: anyone who changed labs into a different unit system. Retention: a trend that silently breaks when you switch labs is a reason to stop trusting (and stop uploading); a trend that visibly survives the switch — with the conversion shown — is a reason to keep the timeline going precisely through the life events (new clinic, new country) that make a precision-health record valuable. (Hypothesis: unit reconciliation raises continued-upload rate among users whose second-or-later lab reports in a different unit than their first, because it removes the silent-breakage failure that otherwise reads as the app being wrong about their own data — back-of-envelope from how the spreadsheet-keeping power user's single biggest manual chore is exactly cross-unit alignment; treat as untested without remote analytics, which we will never add.) The "show me" frame is the spreadsheet-tired persona's: "it converted my metric labs onto my old scale automatically and showed me the factor" is the precise capability their manual spreadsheet exists to provide and no app has automated for them — the same high-LTV, vocal segment the canonicalization receipt (0026) targets, served on the dimension 0026 left open.

## Acceptance criteria

Each box maps 1:1 to a Playwright test scenario.

- [ ] `src/labs/unit-reconcile.ts` (new) exports `reconcileResultUnit(result: Result, marker: MarkerDef): { canonicalValue: number; canonicalUnit: string; reportedValue: number; reportedUnit: string; factor: number; converted: boolean } | null`. When `result.unit` (case/whitespace-normalized) equals the marker's canonical `unit`, it returns `converted: false` (no change needed). When `result.unit` matches one of `marker.altUnits[].unit`, it returns `converted: true` with `canonicalValue = reportedValue × toCanonical`, `factor = toCanonical`, and the canonical unit. When `result.unit` is neither the canonical nor any known alt unit, it returns `null` (no conversion available — the engine must not guess). Pure: no DOM, no Dexie, no network.
- [ ] At result-store time (the extraction-to-panel path and the manual-entry path in `src/pages/labs.ts` / wherever results are normalized before persist), each result whose unit resolves to a known alt unit is stored with its value converted to the canonical unit and its `unit` set to canonical, while the originally-reported value and unit are preserved on the result (additive fields `reportedValue?: number; reportedUnit?: string`). A result already in the canonical unit is stored unchanged. A result in an unknown unit is stored as-is (no conversion, no fabricated factor) and flagged for the receipt's "could not convert" path. Asserted by storing a mmol/L cholesterol result and confirming the persisted `value` is the mg/dL canonical and `reportedUnit` is "mmol/L".
- [ ] The post-extraction panel review screen (`#/labs?id=N`) renders a "Unit reconciled" receipt line for each converted result: "<labName> reported <marker> in <reportedUnit>; converted to <canonicalValue> <canonicalUnit> using ×<factor> to join your line — now <totalDraws> draws on one scale." The receipt section renders under its own eyebrow only when at least one result was converted; a panel entirely in canonical units shows no unit-receipt UI. Asserted by seeding a prior mg/dL cholesterol draw and a new mmol/L draw and confirming the converted line with the correct mg/dL value and factor.
- [ ] A result whose unit is unknown to the marker (no canonical match, no alt match) renders an honest "could not convert" line — "<marker> was reported in <reportedUnit>, which we do not have a conversion for — it is shown as reported and kept off the converted trend." It is never silently dropped and never guessed. Asserted by a result in a fabricated unit confirming the honest line and that the value is stored as-is.
- [ ] The Progress trend (`src/pages/progress.ts`) plots each marker's series in the canonical unit, using the stored canonical values, so a mg/dL draw and a converted-from-mmol/L draw sit on one continuous line. Asserted by seeding two draws in different units for one marker and confirming the sparkline series uses canonical values (one scale), not raw reported values.
- [ ] The receipt and conversion are computed/applied with **zero network calls** — `altUnits` factors ship in the marker DB and the math is local; no inference, no pricing/unit-table fetch. Asserted by storing a convertible result and confirming the mock recorded zero requests during the conversion/receipt render.
- [ ] User-defined markers (0002) participate: a user-defined marker that carries `altUnits` reconciles identically; one without `altUnits` simply has no alt units to match (a non-canonical unit returns `null` → the "could not convert" path). Asserted with a user-defined marker carrying an alt unit.
- [ ] Sex-specific marker keys (e.g. `ferritin_m`/`ferritin_f`) resolve their canonical unit and factors via `findMarker()` against the merged set; the receipt shows the human marker name, not the suffixed key. Asserted with a sex-specific marker converted on a male profile.
- [ ] The originally-reported value/unit remain visible on the result detail (the user can always see what the lab actually printed) — conversion augments, never erases, the source reading. Asserted by confirming a converted result's detail shows both "as reported: <reportedValue> <reportedUnit>" and the canonical value.
- [ ] Renders on both **chromium and mobile-webkit**. The receipt lines and the "as reported" detail wrap cleanly at the 390 px viewport; long unit strings respect `min-width: 0` (the documented overflow fix).
- [ ] Tour mode (0014) surfaces a unit receipt only if the tour fixture is shaped to carry a cross-unit draw (otherwise absent — never fabricated). Shared-view mode (0017) does NOT render panel detail or the receipt. Asserted in both modes.
- [ ] Privacy E2E (`tests/e2e/privacy.spec.ts`) still passes — conversion and receipt are local-only; no new hostnames; no inference call.
- [ ] Schema migration: **yes (additive fields, version bump)** — `Result` gains optional `reportedValue?: number` and `reportedUnit?: string`. Bump the Dexie version with a new `.version(N).stores({...})` block (the `panels` store key path is unchanged; the fields live inside the stored `results[]` objects, so the migration is a no-op upgrade — confirm whether a version bump is strictly required given results are stored as object payloads, and add a migration test asserting existing panels load unchanged with the new optional fields absent). Existing draws (no `reportedValue`) render exactly as today (their stored value already is the value they were drawn at; only future cross-unit draws carry the reconciliation metadata).
- [ ] Existing canonical-unit panels are byte-for-byte unchanged: a panel whose every result was already in the canonical unit produces no unit receipt and stores identical values to today. Asserted against an all-canonical panel.
- [ ] New `tests/e2e/unit-reconcile.spec.ts` covers: mmol/L → mg/dL conversion stores the canonical value, the receipt line with the correct value + factor + draw count, the "could not convert" honest path for an unknown unit, the Progress trend on one canonical scale across mixed-unit draws, both-values-visible on result detail, user-defined + sex-specific reconciliation, zero-network, all-canonical panel unchanged, tour vs shared-view behavior, mobile rendering, and the additive-fields migration.

## Out of scope

Explicit anti-goals. The dev agent will not do these even if they seem related.

- An LLM-driven unit guesser. Conversion is a deterministic table lookup against `MarkerDef.altUnits`; a Claude call would add cost, latency, non-determinism, and an egress to a feature whose entire value is being instant, local, and provably correct. A unit the table does not know is reported honestly as un-convertible, never guessed.
- Inferring the unit when the lab did not state one. If a result has no unit, that is an extraction-quality question for the extractor/manual-entry path, not for this reconciler. This ticket converts *between stated units it recognizes*; it does not assign a unit to a unitless number.
- Expanding the `altUnits` coverage across the whole marker DB in this ticket. The reconciler uses whatever `altUnits` each marker already carries; adding alt-unit factors to more markers is a separate, additive `src/data/markers.ts` ticket (the same way 0002-style marker extensions are their own work). This ticket ships the mechanism plus the receipt; it does not audit the table's completeness.
- Re-storing or back-converting historical panels. Existing draws keep the values they were stored with (which are the values the user already trusts on their charts). The reconciliation applies to draws stored on or after this ships; a one-time historical re-conversion is risky (it would rewrite stored data) and is explicitly not done.
- Name canonicalization. That is 0026's job and is unchanged — this ticket is the unit-axis sibling. The receipt sections are distinct; do not merge them into one line (0026's out-of-scope warns that folding name + unit reconciliation into one line muddies the message).
- Carrying the unit receipt into the doctor PDF (0010/0016), the share link (0017), or the Markdown export (0027). The Markdown export already shows each result's unit and ranges; this is the at-upload reconciliation moment.
- A user-facing "preferred units" toggle (show me everything in mmol/L). The canonical unit is the marker DB's; a global unit-preference layer is a larger, separate design and is not the minimum value here.
